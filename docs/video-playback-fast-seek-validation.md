# 播放低延迟优化验证记录

日期：2026-10-23。分阶段实现基于当前工作树，保留此前的播放页、加载组件及其他未提交改动；未使用 DevSpace 插件。

## 实施范围

| 阶段 | 当前结果 |
| --- | --- |
| P0 | 增加服务端停止、启动、首片与 ready 耗时；浏览器按 seek token 记录真正目标 video 帧，并提供只读 DOM 指标和基准脚本 |
| P1 | 增加 revision 有界长轮询和首片通知；停止/启动移出全局锁；缓存命中快速确认；同代次旧心跳/进度隔离；有界索引回退；修复暂停验帧顺序 |
| P2 | 按完整 MIME 协商 Direct Play；鉴权 Range/HEAD、响应读取租约、模式切换与一次兼容性降级；后台元数据预热和字幕版本缓存 |
| P3 | H.264 SDR 视频流复制、音频复制或 AAC 转码、独立重封装名额、固定 6 秒目标时长与长 GOP 回退；暂停预读至目标帧后才挂起 |
| P4 | 未实现或启用完整占位 VOD。当前没有稳定全局分片边界、跨 job 时间戳和并发缺片仲裁的充分验证，继续使用有限窗口 HLS |
| P5 | 完成同源软硬编码对照；未默认更改编码器、readrate 或引入未经验证的整条 GPU 管线 |

P1 的逐片 FFprobe 和递归容量核对仍保留。它们保障时间戳和配额正确性，本轮没有用未经验证的推导或增量计数替换。

“自动（原画优先）”根据能力选择原文件或流复制；需要完整转码时使用已支持的最高档位，不保证 4K 等片源仍以原始分辨率输出。HDR、ASS/PGS、Safari 原生 HLS 等支持范围未扩展。

## 真实浏览器证据

使用项目固定入口启动隔离测试数据库与合成媒体，前端为 `http://localhost:5174`，API 为 `http://localhost:8100`；原有 5173/8000 服务未被替换。媒体位于 `.cache\fastseek-e2e\run-c97b4203`，不连接真实媒体库或下载器。

在本机 Codex 内置浏览器中，MP4/H.264/AAC 被选为 `direct`，video 直接读取鉴权 `/stream`，播放时钟持续推进。暂停和播放中分别完成 30 次已缓冲区域跳转，全部记录 `video-frame` 证据、保持同一 generation，未把 `seeked` 事件代替帧证据。

| 场景 | 有效样本 | 目标帧 P50 | 目标帧 P95 | 最大值 |
| --- | --- | --- | --- | --- |
| 原文件直放，暂停时缓存跳转 | 30 | 7.0 ms | 10.1 ms | 81.1 ms |
| 原文件直放，播放中缓存跳转 | 30 | 9.2 ms | 11.5 ms | 12.1 ms |

P95 使用排序后 `(N-1)×0.95` 线性插值。这些是本机 1280×720、24 fps、120 秒合成片在浏览器缓存中往返定位的结果，不代表冷 Range、局域网、真实长片或全部客户端的跳转耗时。原始数据为该专用目录下的 `browser-direct-paused.json` 与 `browser-direct-playing.json`。

同源 H.264 MKV 已在浏览器选为 `remux`，正常解码并持续推进媒体时钟。尚未完成它与完整转码的 30 次浏览器目标帧采样。后续浏览器自动化被 Work 设置禁用，测试保留该设置，没有通过其他浏览器或协议绕过。

本地截图位于 `.cache\fastseek-e2e\run-c97b4203\direct.png`，与原始指标一起保留在忽略的测试目录中，不随源码提交。

## 正确性与回归

已覆盖的新增边界包括：

- 原文件 Range 字节准确性、HEAD、206/416、ETag/If-Range、鉴权与跨用户访问隔离、断连释放读取租约。
- Direct Play 不占编码槽或分片缓存；多音轨显式选择；H.264 MKV 的音频复制及音频转码；实际分片独立解码；长 GOP 回退。
- 旧 FFmpeg 停止超时仍保留受管进程引用和文件租约；连续 seek 与启动期间关闭；首片完成即唤醒状态等待者。
- 同 generation 内旧 seek revision 的心跳和进度拒绝；浏览器缓冲确认限于曾发布范围，不允许伪造远处缓存驱动顺序生产。
- 暂停流复制从目标前预读时，先覆盖目标后至少一个视频帧再 ready/挂起；真实 TS 测试阻塞目标片探测，验证前段就绪不会提前暂停。
- 256 kbps 与 1 Mbps 总预算实际约束视频 VBV 参数，并预留音频和封装开销；无上限请求保持原命令。VBV 预算不是 HTTP 瞬时带宽硬限速。
- 后台 FFprobe 和共享字幕提取在工具运行期间持有源读取租约，单个等待者取消不会提前允许文件迁移。
- rVFC 早于 seeked/控制响应、暂停往返、旧 token、低帧率及晚到回调；兼容性降级保留暂停、进度、音量和倍速。

最终播放专项四文件共 **104 项通过**，相关 Python 代码与脚本 Ruff 通过；前端 **79 项通过**，TypeScript 与 Vite 生产构建通过。构建仅有已有的大 chunk 提示，未安装或修改依赖。

此前长联合回归执行了媒体库、改名、迁移、修订、认证和 Web 相关测试：246 通过、2 跳过；唯一失败为回收等待断言过早。该测试现已改为等待 stop_task 完成，再断言进程和租约均释放，随后播放专项重新运行通过。未将这次局部重跑描述为重新执行完整长回归。

## 源码冻结后的真实 HTTP 验证

三种模式各执行 30 轮创建、远距定位、目标数据下载及关闭，全部成功。Direct Play 检查 206 及返回长度；HLS 检查目标范围分片存在，并对每种 HLS 模式的一份下载样本执行真实 FFmpeg 解码。测试通过完整登录 Cookie 和实际 FastAPI HTTP 服务，未绕过认证。

| 模式与片源 | 成功 / 总轮数 | 远跳至服务端 ready P50 / P95 | 远跳至数据下载完成 P50 / P95 |
| --- | --- | --- | --- |
| 原文件直放：720p H.264/AAC MP4 | 30 / 30 | 4.2 / 4.6 ms | 12.1 / 15.4 ms |
| 视频流复制：同源 720p H.264/AAC MKV | 30 / 30 | 976.1 / 1327.1 ms | 994.7 / 1386.5 ms |
| 软件转码：360p HEVC/AAC MKV | 30 / 30 | 1530.9 / 2054.1 ms | 1593.4 / 2192.2 ms |

Direct Play 下载为固定 4096 字节 Range，其他两种下载一个实际目标 TS，传输量不同，不能用此表比较三种模式的下载吞吐能力。目标为全片时长的 80%；HLS 目标未在会话分片缓存内，未清空操作系统文件缓存。这些数据不包含浏览器解复用、解码和呈现，尤其不能把 Direct Play 的控制 ready 当作目标画面已显示。

原始记录位于 `.cache\fastseek-e2e\run-c97b4203\http-modes.json` 与 `http-modes-summary.json`。前一轮在 remux 第 24 次被开发热重载中断、会话返回 404，失败记录保存在 `http-modes-initial-with-reload.json`；随后冻结源码重新运行，未把失败样本静默丢弃后算作同一轮成功结果。

HTTP 测试关闭全部自建会话后，本次进程采样中没有仍读取该合成媒体目录的 FFmpeg/FFprobe。隔离开发服务保留运行，方便检查；它使用测试数据库，不能将其页面内容当作真实媒体库状态。

## P5 编码器评估

冻结源码后，用同一 720p H.264/AAC 合成片分别测试 libx264 与 NVENC；两组各自的创建、服务端缓存跳转、冷跳转均为 30/30 成功，媒体版本和 15 个源码指纹完全一致。冷跳转观察到 ready 的 P95 分别为 1000.8 ms 与 987.1 ms；创建 P95 分别为 827.6 ms 与 2006.8 ms，NVENC 出现更大的长尾。

本轮保留默认 libx264、`readrate 8` 和现有管线。这组数据没有证明切换编码器能稳定改善跳转，也不足以支持增加硬解码、设备侧缩放或放宽读取保护。这是无 HTTP、无浏览器并发的服务端测量，不包含目标帧呈现；原始报告、阶段耗时和全部慢样本见[最终同版本对照](video-playback-fast-seek-benchmark.md#p5最终同版本-720p-对照与决策)。

## 已知验证边界

- 本轮没有重新执行 Linux/Docker、全部浏览器、弱网、30 分钟长播与 Anime4K 目标 Canvas 帧延迟验收；旧交付记录不能替代这些新增模式的复验。
- 常规 HLS 保留实际时间戳映射及有限窗口；完整虚拟清单不默认开启，也不承诺任意片源均可在 1.5 秒内跳转。
- 流复制配额预留依据平均码率估算，继续保留磁盘余量和会话配额检查；不能当作可变码率峰值的硬上限。
- Windows 沙箱仍存在媒体路径/junction 解析问题。相关隔离测试、构建和固定开发入口通过正式授权流程执行；未修改 ACL、全局沙箱或媒体路径安全检查。
